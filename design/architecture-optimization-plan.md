# 架构优化实施计划

更新时间：2026-10-02

**状态：Wave 内容迁移、规则引擎职责拆分和 UI 整合检查已完成。**

## 目标

- 新增 Wave 内容时，Mage、供应牌和 Nemesis 数据有清楚、固定的归属位置。
- 按职责拆分规则引擎大文件，减少查找和修改时的相互牵连。
- 维持现有规则、卡牌 ID、存档兼容和 UI 操作结果。

## 已确认的方向

- The Surface 和 The Returned 暂时继续作为 Wave 9 内容，不添加额外来源分类。
- Wave 1 和 Wave 9 都迁移到统一的按 Wave / 内容类型组织方式，不只给新 Wave 加包装入口。
- 引擎按职责划分，不按 Wave 或 Mage 分割公共规则。
- 每批引擎改动都检查 UI 类型、构建和相关 Playwright 流程；必要时调整适配层，不在 UI 重写规则。

## 实施步骤

### 1. 统一 Wave 内容目录和注册入口

- 将 Mage、供应牌、初始牌、Trinket 和 Nemesis 数据放入对应 Wave 和类别目录。
- 每个 Wave 提供明确的静态内容清单；总注册表合并各 Wave，并检查重复 ID 和缺少的卡牌引用。
- 维持现有卡牌 ID、`GameState`、存档内容以及 `data.ts` 的公开导入方式，避免 UI 和测试被目录迁移牵着改。
- 不增加自动扫描或插件系统；不区分 Surface / Returned 的来源字段。

**状态：完成。** 内容已归入 `wave1/`、`wave9/` 下的 `cards/`、`mages/`、`nemeses/` 和 `special-decks/`；两个 Wave 的 `index.ts` 负责静态汇总，`data.ts` 保留旧导入入口。注册时会检查重复 ID 和 Mage/Nemesis 的卡牌引用；图片生成脚本也已改为从内容源码识别 Nemesis，不再依赖旧文件名。

**检查：** 引擎测试通过；原有 Mage、市场牌和初始牌仍注册；Wave 筛选、Nemesis 图片映射和 UI 构建通过。

### 2. 按职责拆分规则引擎

- 将 `engine.ts` 作为兼容入口，内部逐步迁移到独立职责模块。
- 先迁移边界清楚的初始化、回合流程、牌区、资源与阶段操作；再处理效果执行和玩家决策。
- 效果执行和决策处理需要共享来源、目标、卡牌持有者和暂停状态，拆分时通过明确的上下文传递这些信息，不用当前 UI 视角或卡牌归属推导行动来源。
- 每迁移一组，立即运行引擎测试、UI 类型检查和生产构建；受影响的交互补跑 Playwright。不要把所有逻辑搬完才统一测试。

**状态：完成。** 已按职责拆出牌库、玩家状态、Aether、Breach、目标、区域、对局初始化、Nemesis 回合、效果条件、法术伤害预览、战斗、效果执行和决策恢复。效果执行与决策恢复通过显式运行时依赖连接，原有 `engine.ts` 对外函数继续作为兼容入口；其余回合和玩家操作 API 留在入口文件，供 UI 继续使用。

**检查：** `engine.ts` 从约 7,600 行缩至约 3,000 行。引擎测试、UI 类型检查、生产构建和全量 Playwright 回归均通过（86/86）。生产构建仍有既有的单个 JS bundle 超过 500 kB 提醒，不影响构建成功。

### 3. 处理 UI 大文件

**状态：完成（UI 整合检查）。** `useGame.ts` 仍通过 `@engine/engine` 调用公开兼容入口；界面组件没有绕过入口、直接依赖新拆出的引擎内部模块。引擎公开 API、决策类型和存档结构未改变，因此这次拆分不需要 UI 适配代码。

`PlayerArea.vue`（约 1,500 行）、`useGame.ts`（约 1,400 行）和 `style.css`（约 3,400 行）仍较大。按本计划不因行数直接批量拆分；本次引擎迁移没有暴露需要立刻拆的 UI 职责边界，所以没有改动这些文件。后续出现具体维护问题时，再一次拆一个职责并用现有 UI 回归覆盖。

**检查：** 引擎测试、UI 类型检查、生产构建及全量 Playwright 回归通过（86/86），覆盖正常游戏操作与关键决策流程。生产构建仍有单个 JS bundle 超过 500 kB 提醒，但不影响构建成功；首屏加载优化按用户决定暂缓。

## 完成标准

- Wave 1 和 Wave 9 目录结构一致，新 Wave 可以沿用相同方式接入。
- 引擎对外入口稳定，按职责定位规则文件，不需要在一个超长文件里搜索全部逻辑。
- 引擎测试、UI 类型检查、生产构建及全量 Playwright 都通过。
- 本计划只保留实施范围和完成状态；长期规则继续放在 `dev-guide.md` / `ui/ui-guide.md`，不再新增平行指南。

## 后续：前端 UI 整理计划

**状态：完整完成。** 第 1 至第 4 步完成；第 5 步审查后沿用已有通用组件，没有重复拆分。本节根据 2026-10-02 的前端审计追加到现有计划，避免新建另一份平行计划。

### 目标

- 让布局样式的修改更容易预测，减少后加的规则意外覆盖旧规则。
- 让玩家区域和游戏操作协调代码按职责更容易查找。
- 维持现有视觉、交互、存档和规则行为；拆分本身不改变玩法。

### 审计中看到的重点

- 原 `style.css` 约 3,360 行。审计发现的 Trinket Deck 900px 窄屏定位覆盖发生在最低设计尺寸以下；按确认后的桌面目标，不再为这类窗口增加适配或专项测试。
- `PlayerArea.vue` 约 1,520 行，包含玩家区域的多个界面、法术准备提示、图片预加载和拖动交互。
- `useGame.ts` 约 1,380 行，同时管理共享 UI 状态、存档、撤销、回合流程、操作入口和 Nemesis 流程。
- 准备/移动法术的目标高亮由 UI 自行计算，引擎动作也会验证是否合法；两处规则将来可能不一致。
- `CardDecisionModal.vue` 和 `UiGallery.vue` 较大，但都承担通用组件职责，先观察具体修改痛点，不因行数直接拆分。

### 实施步骤

#### 1. 按职责拆分样式并确定桌面目标尺寸

- 将 `style.css` 改为样式入口，按全局变量、基础布局、Nemesis、Market、玩家区域、控制栏、弹窗、Setup、牌堆、帮助和 Debug Tools 拆分样式文件；保持原有导入顺序，避免整理时改变覆盖结果。
- 删除一条确认完全重复的 Breach hover 规则，不批量清理其他可能有意覆盖的规则。
- 桌面浏览器内容区最低目标定为 1440×900 CSS 像素；推荐 16:9 横屏的 1920×1080 或更高，浏览器最大化或 F11 全屏。更小尺寸不作为开发和验收目标。
- 1280×720 的试验显示 Turn Order 区域挤出可用范围，因此不把它作为最低支持尺寸，也不为它追加布局补丁。

**代码验证：** UI 类型检查和生产构建通过；当前代码的全量 Playwright 回归 86/86 通过。布局试验中，1280×720 的 Turn Order 区域越界，因此将最低设计尺寸定为 1440×900；现有 1440×900、1920×1080、2560×1440 的布局检查通过。Save & Exit 用例现在会先处理随机开局中断，避免 Nemesis 决策弹窗导致测试偶发失败。

**人工验收：** 用户已在 1440×900 和 1920×1080 下检查并调整细节，确认第 1 步完全结束。

#### 2. 统一法术目标提示与引擎校验

- 先检查引擎是否已有可直接复用的法术准备/移动目标查询接口。
- 若缺少通用查询，再增加公开的合法目标查询；UI 用它显示高亮，引擎动作继续做最终校验。
- 不在 Vue 中新增卡牌专属规则，也不改变法术准备规则本身。

**代码验证：** 引擎新增统一的 `getSpellBreachTargets()` 查询，覆盖手牌法术与已准备法术的合法目标；Vue 高亮直接调用此查询，动作提交仍由原引擎操作再次校验。阶段测试覆盖开启/本回合 Focus、空位、已占用可交换位置、关闭 Breach 特殊法术、非法术、缺失来源和非主阶段。引擎全量测试、UI 类型检查、生产构建通过；4 项准备/移动目标浏览器回归通过。

**人工验收：** 用户已确认普通法术与特殊法术的准备/移动目标提示符合预期，第二步结束。

#### 3. 小步拆分 `PlayerArea.vue`

- 保留 `PlayerArea` 作为玩家区域的协调入口，按现有界面边界逐块抽成少量子组件，例如 Breach 区、玩家牌区、控制栏。
- 先移动展示和事件转发，不搬规则判断；拖动逻辑只有在边界清晰时才单独提取。
- 每次只拆一个区域，确认行为一致后再继续，避免一次重写整块玩家界面。

**已完成：** 将底部控制栏抽为 `PlayerControls.vue`，并继续将 Breach 显示、玩家区域牌堆/手牌和 Played/Swap/Develop 区抽为 `PlayerBreachArea.vue`、`PlayerHandArea.vue`、`PlayerZoneArea.vue`。`PlayerArea.vue` 保留为协调入口，负责状态、规则判断和操作处理；子组件接收展示数据并转发事件。手牌区内部的滚轮滚动和居中定位随展示一起移动到 `PlayerHandArea.vue`，法术拖放及规则判断留在父组件。

**代码验证：** UI 类型检查通过；35 项玩家区域、Breach 朝向、手牌操作和法术拖放相关 Playwright 测试通过。最终 91 项 Playwright 全量回归通过，生产构建成功。

**人工验收：** 用户此前确认控制栏拆分没有问题；后续展示组件拆分按用户本轮授权连续完成，并用浏览器回归测试检查行为。

#### 4. 按清晰边界拆分 `useGame.ts`

- 优先拆存档读写和撤销快照，因为这两块边界相对清楚。
- 保留一个明确的共享游戏状态所有者；拆分后的模块通过明确函数协作，不复制状态。
- 只有前两部分稳定后，才评估是否需要继续拆回合流程或 Nemesis 流程；不按函数数量机械拆文件。

**代码验证：** 运行 UI 类型检查、构建及全量 Playwright；重点覆盖新游戏、存档、刷新恢复、撤销、待处理决策恢复和 Nemesis 回合推进。

**已完成：** 将存档类型、localStorage 读写、存档摘要，以及撤销快照创建/复制/比较移到 `game-persistence.ts`。`useGame.ts` 继续唯一持有响应式游戏状态，并负责保存时机、恢复流程和撤销应用；没有复制状态所有者。

**代码验证：** UI 类型检查、生产构建及全量 Playwright 通过（91/91）。回归覆盖 Save & Exit/Resume、Wave 9 状态持久化、Nemesis 中断恢复、Ctrl+Z 与待处理决策流程。两项旧测试原先断言 5:7 像素尺寸，已更新为检查项目统一的 63.5:88 实体卡比例。生产构建仍有单个 JS bundle 超过 500 kB 的提示，不影响构建成功。

**进一步评估：** 没有再拆 Nemesis 回合协调。`continueNemesisTurn()` 负责把引擎的 `advanceNemesisTurn()` 结果同步到 UI phase、日志和下一回合启动；这些动作依赖 `useGame.ts` 的单一响应式状态与保存/撤销边界。继续拆分会把状态协调再分散到新模块，目前没有更清晰、收益更大的边界。

#### 5. 决策弹窗与 Gallery 按需整理

- 只有当某一类决策界面再次需要反复修改时，才按展示类型拆分弹窗内部实现。
- 保留现有通用弹窗外壳、卡牌选择逻辑和 Gallery 示例，不按单张卡牌复制组件。
- 若改动共享组件，同步更新 Gallery，并用对应截图和浏览器测试检查。

**检查结果：** `CardDecisionModal.vue` 已使用 `CardSelectionPanel.vue`、`LargeCardChoicePanel.vue`、`TokenAmountChoicePanel.vue`、`TwoButtonChoice.vue`、`MageAbilityChoice.vue` 和 `TurnOrderTokenRow.vue` 承担可复用的选择展示；对应模式也已在 Gallery 中展示。弹窗主体负责把 typed decision 映射到这些组件，并保留少量专属决策分支。当前没有一个仍反复修改、又能独立于共享状态和决策处理抽出的剩余展示类型，因此本阶段不再增加转发层或重复组件。

**代码验证：** 91 项全量 Playwright 与 Gallery 回归通过；引擎测试、UI 类型检查和生产构建通过。一次全量回归发现 Qu Form 测试没有处理随机供应卡自己的 on-gain 决策，已让测试先完成前置选择，并单独重跑及全量重跑通过。

**视觉复查记录：** Gallery 浏览器回归通过。用户本轮授权在无法使用电脑时继续完成计划，因此本轮没有暂停等待人工逐项查看；没有把自动化截图测试记作人工验收。
